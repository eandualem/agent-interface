# Protocol fixtures

One JSON file per published shape. Backbone and Agent Interface both decode
every file into its type and encode it back to the same JSON
(`tests/fixtures.rs` on this side). A shape changes only additively; a new
version of a shape gets a new file.

| File | Endpoint or use | Type | Compared with Agent Backbone 0.5.1 |
|---|---|---|---|
| `error.json` | Every reply that is not a success | `error::ErrorBody` | Same envelope. Every error now has a `code`; 0.5.1 gave most errors a plain-text `detail`. |
| `profile.json` | `GET /api/profile` | `profile::ProfileIdentity` | New. Replaces the profile binding (installation and lifecycle IDs, binding headers). |
| `discovery.json` | `<dir>/profiles/<profile_id>/discovery.json` | `discovery::DiscoveryFile` | New. Replaces the profile registry. `credential_reference` says what a client presents on the socket to say who it is; today always `{"type": "socket"}`: nothing, the service knows the process that connects. A served entry of the machine's `GET /api/profiles` carries the same fields. |
| `machine-profile-create-first.json` | The body of the machine's `POST /api/profiles`, for a first profile | `machine::CreateProfile` | New. `starter` (`core-v1`) is installed in the new profile; with `only_if_none` the profile is created only on a machine with none. 201 means, and only means, that this request created a profile: a repeat of it under its request ID is answered with that profile again. |
| `error-profile-exists.json` | The refusal of an `only_if_none` creation on a machine with a profile (409) | `error::ErrorBody`, fields `machine::ExistingProfiles` | New. Nothing was created. `profiles` lists every profile here as `GET /api/profiles` does, a failed one included: any profile kept on the machine counts. |
| `machine-stopping.json` | The reply to the machine's `POST /api/machine/stop` (202) | `machine::Stopping` | New: `backbone down` asks the service to stop through it. Any request after it is refused at once with `unavailable`, and the process ends cleanly. |
| `secrets.json` | `GET /api/secrets` | `secrets::SecretList` | New: names only, as 0.5.1's `secrets list` printed them: the secrets Backbone reads, set or not, then any other that is set. The operator's only; the profile's home keeps them. |
| `secrets-reported.json` | `GET /api/secrets` | `secrets::SecretList` | New: what the parts of the home that use the secrets said of them. A set secret with neither field is in use, or nothing reports on it; `problem` is the last trouble reported (`code`, a `message` written by Backbone, and the diagnostics `source` it came from as `connection`); `verdict: "pending"` means nothing has spoken for the value now stored yet, so read again. Never both; an unset secret has neither. Unknown codes and verdicts decode to a fallback. |
| `secret-value.json` | The body of `PUT /api/secrets/{name}` | `secrets::SecretValue` | New. The value is never in a reply, a log line, a diagnostic or an error. Unknown fields are refused. |
| `setup-initialize.json` | A `backbone setup` request: `initialize` | `setup::SetupRequest` | Changed: schema version 3, a UUIDv7 `request_id`, and `profile_name` in place of 0.5.1's `data_dir`. Unknown fields are refused. |
| `setup-first-agent.json` | A `backbone setup` request: `first_agent` | `setup::SetupRequest` | Changed: schema version 3, `profile_id` names the profile, and no `hooks`. `model` must be there, `null` or not. |
| `setup-first-agent-orchestrator.json` | A `backbone setup` request: `first_agent` whose agent is a top-level orchestrator | `setup::SetupRequest` | New. `agent.orchestrator` is `true`: the agent is placed directly under the owner as an orchestrator in the same write that registers it, and so reads every repository the profile's GitHub connection reaches. Left out or `false`, it is a main agent. Only setup takes it: `POST /api/agents/start` has no such field. It is part of the request: the same `request_id` with another `orchestrator` is refused as a changed request. |
| `setup-cancel-first-agent.json` | A `backbone setup` request: `cancel_first_agent` | `setup::SetupRequest` | The saved `first_agent` request with only `action` changed: its `request_id` stays the original one. The CLI sends a fresh UUIDv7 only as the request's header, of its own. |
| `setup-cancel-join-profile.json` | A `backbone setup` request: `cancel_join_profile` | `setup::SetupRequest` | New. The saved `join_profile` request with only `action` changed: its `request_id` stays the original one, which is the join's ID on the machine. |
| `setup-event-step.json` | A `--jsonl` line: a step | `setup::SetupEvent` | Same shape, schema version 3. |
| `setup-event-result.json` | A `--jsonl` line: the result | `setup::SetupEvent` | Same shape, schema version 3. `initialize` reports `backbone_dir` and `profile` (the discovery file), not 0.5.1's `data_dir` and `api_url`. |
| `setup-join-profile-code.json` | A `backbone setup` request: `join_profile` with a join code | `setup::SetupRequest` | New. `join` is a `joining::JoinStart`, and takes only its form's fields. |
| `setup-join-profile-discovery.json` | A `backbone setup` request: `join_profile` with a profile `discover_profiles` listed | `setup::SetupRequest` | New. The owner approves the join after comparing a six-digit number. |

| `setup-event-discovered.json` | A `--jsonl` result: the profiles announced on the local network | `setup::SetupEvent`, data `setup::DiscoveredData` | New. `retry` is `same_request`: sending it again looks again. |
| `secret-changed.json` | The reply to `PUT` and `DELETE /api/secrets/{name}` | `secrets::SecretChange` | New. `was_set` tells a value added from one replaced, and one removed from one that was not set. |
| `secret-changed-problem.json` | The reply to a `PUT /api/secrets/{name}` | `secrets::SecretChange` | New: the value was stored and the change taken into use, but what uses it cannot: here a GitHub App ID that is not a number, shown on that secret alone. The reply comes once what reads the secret has spoken, or after 5 seconds. |
| `secret-changed-pending.json` | The reply to a `PUT /api/secrets/{name}` | `secrets::SecretChange` | New: the value was stored, but what reads it had not taken it into use within the 5 seconds the reply waits, as during a long GitHub pass, or a later write of the same secret overtook it. `GET /api/secrets` tells later. | `secret-removed-pending.json` | The reply to a `DELETE /api/secrets/{name}` | `secrets::SecretChange` | New: the secret was removed from the file, but what used it had not let it go within the 5 seconds the reply waits, as when a GitHub pass under way still runs with it, or a later write of the same secret overtook the removal. Read the list again later; the unset entry carries neither field. Without `verdict`, a `DELETE` reply means the value is no longer used. |
| `agents.json` | `GET /api/agents` | `agents::List<agents::Agent>` | Same shape, plus `machine`, `waiting` and `background`. `waiting` is what the agent waits on outside itself, `null` when nothing: `on` is one line shown as written, such as `build slot`; `on_agent` names an agent only when `on` is `agent`; `reason` is one line of at most 200 characters; `since` is RFC 3339 in UTC. `background` counts the agent's queued and running runs (`runs.json`) and the processes below its pane other than its CLI. `role` and `superior` say where the agent stands below the owner: its role, `null` for a session that is not registered, and the name of the agent directly above it, `null` directly under the owner. `mode`, `grants`, `ceiling` and `reach` are what the agent may reach, as `access::AgentAccess` has them. New: `takes_issues`, `false` for an agent set to take no issues, which is delivered nothing from GitHub, and `true` otherwise, a session that is not registered included; read as `true` when absent. New: `restart`, the agent's restart while one is under way, left out otherwise (`agents-restarting.json`). New: `held_queue`, the agent's terminal deliveries held behind one, `null` when nothing holds them (`agents-held-queue.json`): `reason` is `uncertain_delivery`, a delivery whose text may be at the agent's prompt; a reason a client does not know means deliveries are held, cause not known. `since` is when it began to hold them (RFC 3339, UTC); `count` is how many messages wait behind it, not counting it, so 0 is one held and none behind; `message` is the held delivery's receipt, written as an inbox `ack_token` is, which `.../queue/resubmit` and `.../queue/clear` take. Its changes are sent on `agent.changed` within one agent-monitor pass (60 s by default). |

Every reply about a sign-in has these fields. Only the home asks GitHub, at `interval_seconds` at least, which GitHub may lengthen; reading the sign-in more often never makes it ask sooner. A repeat of the start under its request ID is answered with this same reply, and the request record keeps it: never the device code or a token. After the home restarts, the ID is `not_found`. |
| `github-signin-connected.json` | `GET /api/github/sign-in/{id}` once the token is saved | `github_signin::SignIn` | New. `account.scopes` is what GitHub granted. `activation` is `in_use`: the gate and the intake took the token into use, with no restart. `repository_access` has one entry for each repository the start asked to check, empty for none; `readable` proves that read alone. |
| `github-signin-sso-required.json` | A connected sign-in with a repository whose organization enforces SAML single sign-on | `github_signin::SignIn` | New. The token is saved all the same. `action_url` is built for github.com from the organization's name, never copied from GitHub's reply. `state` is one of `readable`, `sso_required`, `authorization_required`, `forbidden`, `unavailable_or_hidden` and `check_failed`; a 404 is `unavailable_or_hidden`, never taken as proof of a refusal. |
| `github-signin-expired.json` | A sign-in whose code expired before it was approved | `github_signin::SignIn` | New. `problem.code` is a reason of the sign-in, not an error code of the reply. The credential before it stands. |
| `github-signin-refused.json` | A sign-in the person refused on GitHub | `github_signin::SignIn` | New. `problem.code` is `access_denied`. The credential before it stands. |
| `github-signin-failed.json` | A sign-in that ended without a saved token for another reason | `github_signin::SignIn` | New. `problem.code` is one of `client_rejected`, `device_flow_disabled`, `invalid_device_response`, `github_unavailable`, `insufficient_scopes`, `unsupported_token_expiry`, `credential_changed`, `credential_store_failed` and `credential_store_uncertain`. Only `credential_store_uncertain` may leave the credential before it replaced. No account is given for a sign-in that did not connect. |
| `github-signin-client-missing.json` | The refusal of a start while the profile has no OAuth App client ID (503) | `error::ErrorBody`, fields `github_signin::Unconfigured` | New. `setting` names the setting to set. GitHub is not asked anything. |
| `github-signin-credential-exists.json` | The refusal of a start without `replace` while the profile has a `GITHUB_TOKEN` or a GitHub App (409) | `error::ErrorBody`, fields `github_signin::SignInConflict` | New. Nothing started. |
| `github-signin-pending-conflict.json` | The refusal of a start while another sign-in is pending (409) | `error::ErrorBody`, fields `github_signin::SignInConflict` | New. `sign_in_id` names the pending sign-in, which a client reads to show its code again. Nothing started. |

`GET /api/sheets/{sheet_id}/export` returns the file itself, not JSON, so it
has no fixture. Its `X-Backbone-Sheet-Warnings` header holds the same JSON
array of strings as an import's `warnings`.
